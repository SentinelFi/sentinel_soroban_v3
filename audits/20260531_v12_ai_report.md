## V12-CF-01: Post-Oracle Cancellation Purchases Can Drain Vault Payouts

**Severity:** Critical

**Status:** Confirmed

**Affected code:**

- `contracts/controller/src/purchase.rs::buy_insurance`
- `contracts/oracle_aggregator/src/lib.rs::set_cancelled`
- `contracts/oracle_aggregator/src/lib.rs::register_flight`
- `contracts/flight_pool_manager/src/lifecycle.rs::add_buyer`
- `contracts/controller/src/settle.rs::execute_settlements`
- `contracts/flight_pool_manager/src/claim.rs::claim`

**Issue:**

`buy_insurance` validates route terms and minimum lead time but never checks the current oracle status for the `(flight_id, date)` being purchased. `oracle.register_flight` is idempotent: if the oracle row already exists, it extends TTL and returns without rejecting based on status.

This allows purchases after the authorized oracle has already marked a registered flight as `Cancelled`, as long as pool status is still `Active` and keeper settlement has not yet run. `add_buyer` checks only the pool `FlightConfig.status`, not the oracle outcome.

**Why this is real:**

- The oracle can transition `Active -> Cancelled`.
- A later purchase for the same `(flight_id, date)` calls `oracle.register_flight`, which returns on existing data instead of rejecting.
- `pool.add_buyer` accepts the buyer while the pool config remains `Active`.
- `execute_settlements` funds cancelled payouts based on `cfg.buyer_count`.
- The late buyer can claim the full payoff.

**Impact:**

Users can buy after cancellation is known and receive a guaranteed payout. Repeated late buyers can drain vault funds up to available solvency capacity, paying only the premium while claiming the full payoff after settlement.

**Recommendation:**

Before accepting a purchase, read oracle flight status and reject any status other than `NotInitiated` or `Active` as appropriate for the business model. At minimum, reject `Cancelled`, `Landed`, `ToBeSettled*`, and `Settled`. Also consider closing purchase admission once oracle data has been reported or once the flight date is too close, independent of owner-configured minimum lead time.

## V12-CF-02: Claim-Window TTL Extension Can No-Op, Archiving FlightConfig Before Claims Close

**Severity:** High

**Status:** Confirmed

**Affected code:**

- `contracts/flight_pool_manager/src/storage.rs::extend_flight_ttl_to`
- `contracts/flight_pool_manager/src/settle.rs::settle_with_claim_window`
- `contracts/flight_pool_manager/src/claim.rs::claim`

**Issue:**

`extend_flight_ttl_to` computes an `extend_to` value intended to keep `FlightConfig` alive through `claim_expiry + 30 days`, but calls:

```rust
extend_ttl(&key, PERSISTENT_TTL_THRESHOLD, extend_to)
```

where `PERSISTENT_TTL_THRESHOLD` is about 7 days. Soroban TTL extension only takes effect when the key's remaining TTL is below the threshold. If a flight is settled delayed/cancelled soon after purchase, the `FlightConfig` can still have roughly 31 days of TTL remaining, which is above the 7-day threshold. The extension to the longer claim-window TTL can therefore no-op.

The claim path must read `FlightConfig` before checking `claim_expiry`, so an archived config makes valid claims fail even while the claim window should still be open.

**Impact:**

For delayed/cancelled flights settled shortly after purchase, `FlightConfig` can expire before the configured claim window closes. Buyers then cannot claim because the contract panics on missing config. This can cause direct loss of valid payouts.

**Recommendation:**

Use an extension threshold that guarantees extension when `extend_to` is larger than the current intended lifecycle, or call TTL extension at a point where the threshold condition is satisfied. A practical fix is to pass `extend_to` as both threshold and extension target for claim-window-critical keys, or otherwise ensure the key is extended whenever current TTL is less than the required claim-window lifetime.

## V12-CF-03: Long-Dated Policies Can Outlive Pool Config and Buyer Proof TTLs

**Severity:** High

**Status:** Confirmed

**Affected code:**

- `contracts/controller/src/purchase.rs::buy_insurance`
- `contracts/flight_pool_manager/src/storage.rs`
- `contracts/flight_pool_manager/src/lifecycle.rs::add_buyer`
- `contracts/flight_pool_manager/src/claim.rs::claim`
- `contracts/controller/src/settle.rs::classify_flights`
- `contracts/controller/src/settle.rs::execute_settlements`

**Issue:**

`buy_insurance` enforces only a minimum lead time and has no maximum booking horizon. The pool `FlightConfig` receives a default TTL of about 31 days on registration/add-buyer, and the buyer proof receives a fixed 180-day TTL. Both TTLs can be shorter than the lifecycle of an arbitrarily future-dated policy.

**Impact:**

Long-dated purchases can lock vault collateral and later lose the pool config or buyer proof needed to settle and claim. Missing pool config can also revert keeper classification/settlement loops. Missing buyer proof causes `claim` to fail with `no policy`.

**Recommendation:**

Add a maximum booking horizon and align all policy storage TTLs to the maximum lifecycle: booking horizon, flight processing window, claim window, and safety buffer. Reject purchases whose lifecycle cannot be safely represented by on-chain storage TTL.

## V12-CF-04: Unbounded Flight Registrations and Active-List Scans Can Freeze Settlement and Capital

**Severity:** High

**Status:** Confirmed

**Affected code:**

- `contracts/controller/src/settle.rs::classify_flights`
- `contracts/controller/src/settle.rs::execute_settlements`
- `contracts/oracle_aggregator/src/lib.rs::register_flight`
- `contracts/oracle_aggregator/src/lib.rs::prune_settled`
- `contracts/flight_pool_manager/src/lifecycle.rs::register_flight`
- `contracts/flight_pool_manager/src/storage.rs::prune_active_list`

**Issue:**

The oracle and pool store active flights in unbounded vectors. The controller keeper paths fetch and scan the full oracle active list in a single transaction. Pool settlement also calls a linear prune helper on its active list.

**Impact:**

Attackers or heavy normal usage can make classification, settlement, and cleanup exceed Soroban resource limits. Because collateral unlocks happen only in settlement, this can freeze underwriter capital and delay or block traveler claims.

**Recommendation:**

Replace unbounded full-list processing with bounded batches, cursors, and stage-specific queues. Avoid vector-wide mutation in settlement hot paths.

## V12-CF-05: Route Identity Drops Origin/Destination in Pool and Oracle Keys

**Severity:** Medium

**Status:** Confirmed

**Affected code:**

- `contracts/governance_module/src/storage.rs::DataKey::Route`
- `contracts/controller/src/purchase.rs::buy_insurance`
- `contracts/flight_pool_manager/src/storage.rs::PoolKey::FlightConfig`
- `contracts/flight_pool_manager/src/storage.rs::PoolKey::Buyer`
- `contracts/oracle_aggregator/src/lib.rs::register_flight`

**Issue:**

Governance authorizes routes by `(flight_id, origin, dest)`, but pool and oracle state are keyed only by `(flight_id, date)`. The controller validates a full route, then drops `origin` and `dest` when registering downstream state.

This creates collisions between distinct approved routes sharing the same flight ID and date.

**Impact:**

If two approved routes share a `flight_id` and date:

- Different terms cause the second route's purchase to revert because the existing pool config has different terms.
- Same terms can merge buyers into one pool/oracle lifecycle even though governance treated the routes as distinct.
- A buyer can be blocked from buying two distinct route policies with the same `flight_id/date` because buyer proof is keyed without route dimensions.

This is primarily a correctness and availability issue unless the business model expects `flight_id` alone to be globally route-unique.

**Recommendation:**

Make downstream identity match governance identity. Include `origin` and `dest` in pool/oracle keys and active-list entries, or enforce at governance level that a `flight_id/date` can only correspond to one route.

## V12-CF-06: Mutable Governance Defaults Can Invalidate Partially Defaulted Route Economics

**Severity:** Medium

**Status:** Confirmed, trusted-owner/operator-triggered

**Affected code:**

- `contracts/governance_module/src/lib.rs::set_defaults`
- `contracts/governance_module/src/lib.rs::whitelist_route`
- `contracts/governance_module/src/lib.rs::route_status`
- `contracts/governance_module/src/storage.rs::resolve_terms`
- `contracts/flight_pool_manager/src/lifecycle.rs::register_flight`
- `contracts/controller/src/settle.rs::execute_settlements`

**Issue:**

Routes can store `None` for premium, payoff, and delay fields, resolving those fields from mutable defaults at read time. Route writes validate the resolved terms at write time, but `set_defaults` does not revalidate existing partially-defaulted routes.

After defaults change, an existing route can resolve to terms that would not pass `payoff > premium`. The controller then registers those terms in the pool. Pool registration checks only positive premium/payoff, not `payoff > premium`. During delayed/cancelled settlement, the controller computes `payoff - premium`, which underflows and reverts when `payoff < premium`.

**Impact:**

Owner default changes can silently brick future settlement for affected partially-defaulted routes. This is not an unprivileged exploit, but it is a real configuration hazard that can freeze claims and collateral.

**Recommendation:**

Either store fully resolved immutable terms on each route, or revalidate every active route affected by a default update. Also enforce `payoff > premium` at pool registration as a defense-in-depth check.
